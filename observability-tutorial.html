Section 02

Background: what problem are we solving?

The story

Imagine you run a small pizza website. One Saturday night, customers start complaining that the site is slow. You log in to the server and stare at it. Is the processor busy? Is the database slow? Did a bug start throwing errors ten minutes ago, or has this been happening all week?

Without instrumentation you are guessing. Observability is the practice of making a system explain itself, so you can answer those questions without guessing and without needing to be logged in at the exact moment things break.

The three kinds of data

PillarWhat it isEveryday analogyTool
MetricsNumbers measured over and over (CPU 42%, 130 requests/sec)The dashboard in a carPrometheus
LogsLines of text describing single eventsA diary, or a shop's receipt rollLoki
TracesThe path one request took through many servicesA parcel tracking pageTempo / Jaeger

And you need something to look at all of it. That is Grafana.

Metrics or logs — why not just one?

This confuses beginners more than anything else, so here is the core idea:

  • Metrics are small and cheap. A CPU number recorded every 15 seconds for a year is only a few megabytes. You can keep metrics for everything and graph them instantly — but a metric cannot tell you which customer hit the error or why.
  • Logs are big and detailed. A log line has the user ID and the stack trace. But storing every line from every server is expensive, and searching all of them is slow.

So the professional workflow is: metrics tell you that something is wrong and when; logs tell you why. You spot a spike on a graph at 21:03, then read the logs from 21:03.

Section 03

The three tools in plain English

Prometheus — the number collector

Prometheus is a time-series database plus a scraper. Every 15 seconds (you choose the interval) it visits a URL on each machine or application — usually http://the-machine:9100/metrics — and copies down the numbers it finds there, stamped with the time. You then ask questions using a query language called PromQL.

A metrics page is literally just text served over HTTP:

Each line is a metric name, then labels in curly braces, then a number. The labels are what make it powerful: later you can ask for only status="500" requests, grouped by method.

Loki — the log collector

Loki is often described as "Prometheus, but for logs", and that is accurate in one specific way: Loki indexes labels, not words.

Traditional log systems build a giant index of every word in every line, which is powerful but expensive — the index can end up as large as the logs. Loki instead compresses log lines into chunks in cheap object storage such as Amazon S3, and indexes only a small set of labels like {app="checkout", env="prod"}. When you search, it uses the labels to pick a small pile of chunks and then greps inside them. The result is far cheaper storage and fast queries — provided you label things sensibly.

Grafana — the screen

Grafana is the web interface. It connects to data sources (Prometheus, Loki, CloudWatch, MySQL and 150-plus others), draws dashboards and sends alerts. It stores none of your metrics or logs itself; it asks the other systems and draws the answers.

How they fit together

One sentence

Section 06

Prometheus in depth

What it actually is

Prometheus is a single program written in Go that does four jobs: service discovery (work out what to scrape), scraping (fetch /metrics on a schedule), storage (write samples to a local time-series database), and rules (evaluate expressions and fire alerts).

It is deliberately not clustered, not long-term storage, and not a log system. When one server is no longer enough, you either shard it or forward the data to Mimir, Thanos, VictoriaMetrics or Amazon Managed Service for Prometheus.

The four metric types

HistogramCounts observations into bucketshttp_request_duration_seconds_buckethistogram_quantile()

Beginner trap

Graphing a counter directly gives a boring line that climbs forever. rate(counter[5m]) is what you actually want: "how many per second, lately".

Section 07

Loki in depth

The mental model

  • A stream is one unique combination of labels. Every line with the same labels joins the same stream.
  • A chunk is a compressed block of one stream's lines, flushed to storage when it is full or old.
  • The index records only label sets and time ranges, which is why it stays small.

Deployment modes

ModeWhat runsGood for
MonolithicOne process containing everythingUp to roughly 100 GB per day; labs and small teams
Simple scalableRead / write / backend targetsMid-size — but this mode is being deprecated before Loki 4.0
MicroservicesDistributor, ingester, querier, query-frontend, compactor, index-gateway, rulerLarge scale and high availability; what Grafana Labs runs internally

Start monolithic. Grafana now recommends going straight to microservices for production rather than adopting simple-scalable, since that mode is on its way out.

Storage configuration

The current recommended setup is a TSDB index with schema v13 on object storage. For AWS:

Never do this

Never edit an existing schema_config entry. To change schema, append a new entry with a future date. Loki then reads old data with the old rules and new data with the new rules. Editing history silently corrupts queries.

Retention and deletion

An S3 lifecycle policy can act as a safety net, but be careful: deleting objects behind Loki's back causes query errors. Prefer Loki-managed retention.

Section 11 · AWS

EC2 and Launch Templates

What a launch template is, and why it matters here

A launch template is a saved recipe for an EC2 instance: which image, which instance type, which security groups, which IAM role, and — most importantly for us — a user-data script that runs automatically the first time the instance boots.

That last part is the whole trick. Instead of connecting to every new server to install monitoring agents, you bake the installation into the template. Every instance launched from it, whether by hand, by an Auto Scaling Group or by a pipeline, arrives already monitored.

The four golden signals

Design dashboards around these rather than around whichever metric was easiest to collect.

SignalQuestionTypical query

Alert design rules

  • Alert on symptoms, not causes. "Checkout error rate is 8 percent" wakes the right person. "CPU is 91 percent" often does not matter at all.
  • Always use for:. A thirty-second blip is not an incident.
  • Every alert needs an owner and a runbook link in its annotations. An alert nobody knows how to fix trains people to ignore alerts.
  • Route by severity: critical to a pager, warning to chat, informational to a dashboard only.
  • Review firing history monthly and delete alerts that never led to an action.
Section 14

PromQL and LogQL cheat sheets

PromQL

Golden rules

Wrap counters in rate(); use a range at least four times your scrape interval; and always sum after rate, never before.

LogQL

Performance rules: narrow the time range, use the most specific labels you have, put string filters before parsers, and avoid regular expressions when a plain "contains" filter will do.

Section 15

Best practices

Naming and labels

  • Use the same label names everywhere: env, cluster, service, namespace, instance. This is what makes moving from a metric to its logs one click instead of a research project.
  • Metric names in snake_case, base units (_seconds, _bytes), counters ending in _total.
  • Set external_labels on every Prometheus and every Alloy so data merged into a central store is never ambiguous.

The single most important rule: cardinality

Cardinality is the number of unique label combinations. Every unique combination is a separate time series in Prometheus, or a separate stream in Loki, and your cost and failure risk grow with it.

Never use as a label

User ID, request ID, trace ID, session ID, a full URL with query parameters, a timestamp, an IP address, an error message, a pod IP.

Put the unique details in the log line or in Loki's structured metadata, not in labels. Check your worst offenders with:

Retention strategy

DataTypical retentionWhere
Raw metrics15 to 30 daysPrometheus local disk
Downsampled metrics1 to 2 yearsMimir, Thanos or Amazon Managed Prometheus
Application logs7 to 30 daysLoki on S3
Audit and compliance logs1 to 7 yearsS3 Glacier, kept separate from Loki

Security

  • Prometheus, Loki and Alertmanager ship with no authentication. Assume anything that can reach them can read everything. Keep them on private networks behind a proxy that terminates TLS and checks identity.
  • Grafana: single sign-on, no anonymous access, rotated admin password, least-privilege data source permissions.
  • Encrypt S3 buckets, block public access, use IAM roles instead of static keys everywhere.
  • Scrub secrets before they are written to logs — the cheapest place to fix a leaked token is in the application.

Reliability

  • Do not monitor your monitoring only with itself. Add a dead-man's switch: an alert that is always firing, and a receiver that pages you if it ever stops arriving. kube-prometheus-stack ships one called Watchdog.
  • Run two Prometheus servers scraping the same targets for high availability; Alertmanager deduplicates the alerts.
  • Put Loki chunks in S3, not on an instance disk. Instances die; buckets do not.
  • Test your restores. A backup you have never restored is a rumour.

Cost control

Drop noisy logs at the agent with stage.drop — health checks and static-asset access logs are usually more than half of all volume. Use recording rules for expensive dashboard queries, and sample high-volume debug logs rather than discarding the whole category.

Troubleshooting

Prometheus

SymptomCheck
Target down, "connection refused"Is the exporter running? curl http://target:9100/metrics from the Prometheus host
Target down, "context deadline exceeded"Firewall or security group, or the target is slower than scrape_timeout
Target is up but the graph is emptyMetric name typo, or the time range predates the data — try the bare metric name with no filters
"out of order sample" errorsTwo scrapers writing the same series, or clock skew — check time synchronisation
Prometheus runs out of memoryToo many series. Find them with topk(10, count by (__name__)({__name__=~".+"})) and drop the worst

SymptomCheck
Empty results, or "no such table"The schema from: date is in the future, or an existing schema entry was edited

The general debugging ladder

  1. Is the process running? (docker compose ps, kubectl get pods, systemctl status)
  2. Is it healthy? (/-/healthy, /ready, the Alloy UI)
  3. Can the collector reach the target? (curl from inside the same network)
  4. Is data arriving? (the targets API for Prometheus, the labels API for Loki)
  5. Is the query right? (test the simplest possible query in Explore)

Work top to bottom. Jumping straight to step five is why debugging takes hours instead of minutes.

One-page quick reference

The three sentences that matter most

1. Metrics tell you that something broke; logs tell you why.
2. Labels are cheap only when they have few possible values — never put IDs in labels.
3. Pin your versions, keep configuration in Git, and never expose Prometheus or Loki to the internet.
